# Phase 4 Plan

作成日：2026-09-24
更新日：2026-09-24

本書はPhase 4「履歴の確認とMVPの受入検証」をレビュー可能な変更単位へ分けた実行計画である。Phaseの進捗は[Implementation Plan](../IMPLEMENTATION_PLAN.md)だけで管理する。振る舞いの正本は[Product Spec](../PRODUCT_SPEC.md)、状態と集計の正本は[Domain Model](../DOMAIN_MODEL.md)、保存契約の正本は[Persistence Schema](../PERSISTENCE_SCHEMA.md)とし、本書で別の仕様を定義しない。[Phase 3 Plan](PHASE3_PLAN.md)は完了済みの過去資料としてアーカイブに置く。

## 1. 到達点と範囲

Phase 3でCurrent Task、Quick Start、Distraction／Return、中止、手動Breakと、保存・復元・再試行をTUIから操作できるようになった。Phase 4では、Product Specの4指標を利用者がTUIから確認でき、保存したSession・eventと表示が一致することを、一連の操作から再起動まで検証する。仕様第10節の7つの確認例を受入の対象とする。

| 最小振り返り指標 | 集計の正本 | 現状とPhase 4で確認する点 |
| --- | --- | --- |
| 記録上の作業時間 | Focus・Quick Startの`Session.elapsed_ms`。現在のSessionも含む | `ReflectionSummary.work_ms`は計算済み。現在のHistory欄は分未満を切り捨てて表示し、狭い端末では隠れる。短い作業も読み取れる表示にする |
| Focus自然完了数 | 終了済みFocusの`SessionOutcome::Completed` | `completed_focus_sessions`は計算済み。中止・Reset・Skip、Quick Start完了を数えないことを表示と保存記録で照合する |
| Distraction申告数 | Distractionの`InterruptionStarted` event | `distractions`は計算済み。現在のSessionの申告と未復帰の申告も含める |
| Return数 | `Returned`の`InterruptionEnded` event | `returns`は計算済み。中止や再起動だけでReturnを増やさない |

`pomodoro-core`の`ReflectionSummary`と`DomainState::reflection()`が集計し、TUIの`App::reflection()`は履歴部分をキャッシュして現在のSessionを加える。現行の`ui.rs`はHistory欄を表示するが、操作案内を優先する幅では非表示にする。保存待ち中はcontrollerの採用済み状態を表示し、未確定候補を表示に混ぜない。通常tick中の値は現在の状態に従って動くため、画面上で全値をディスク保存済みと誤認させる表現は使わない。

日別集計、詳細履歴一覧、平均Recovery Time、継続率などの追加統計はMVPの必須範囲に含めない。集計結果をV1ファイルへ別の正本として保存せず、既存のSession・eventから導出する。V1形式の変更や旧形式からの移行も予定しない。

## 2. 表示と保存境界の実装方針

- 通常操作中に`h`で振り返り画面を開き、`h`またはEscで閉じる。4指標を英語の固定ラベルで並べ、現在の種別やラウンドとは区別する。既存のHistory欄は補助表示として維持してよいが、それが隠れる端末でも振り返り画面から4指標を確認できるようにする。
- 作業時間は`H:MM:SS`形式とし、秒未満は表示だけで切り捨てる。ドメインのミリ秒値は変更しない。0・999ミリ秒・59秒・61秒・27分などの境界をテストし、表示精度をREADMEに明記する。
- 表示の開閉はSession・event・保存ファイルを変更しない。開いたままでも通常のtickは続き、PauseやDistraction中の時間は作業時間に加わらない。作業名・設定の編集画面と入力を競合させない。
- 入力の優先順位は未保存終了の確認、保存待ち、作業名・設定の編集、振り返り画面、通常操作の順にする。保存失敗が起きたら振り返り画面より`r`再試行と`Q`未保存終了の案内を優先する。振り返り画面から`q`などの通常操作へキーを漏らさない。
- 画面幅と折り返し後の必要行数を確認し、4指標と閉じる操作が収まらないときは端末拡大の案内を出す。復旧キーやエラー理由を押し出さない。描画は時計や保存状態を変更しない。
- 履歴集計に失敗した場合は0と表示せず、失敗理由を示す。現在のSessionを含む集計、履歴キャッシュの更新、保存再試行後の表示は既存のcore・controller境界を使う。

このキー割当と表示の詳細はPhase 4のUI実装案であり、Product SpecやV1保存形式の変更ではない。操作案内とテストを同じPRに含めて確定する。

## 3. レビュー単位と依存関係

4-0で計画を定め、4-1で利用者が集計を確認できる画面を用意する。4-2と4-3はその画面とPhase 3の操作経路を使って仕様例を検証し、4-4で案内と終了条件を揃える。レビュー単位が大きくなる場合も、利用者の操作・保存結果・テストを分離せずに分割する。

### 4-0. 実行計画と現状の確認

- **対象**：本書、Implementation Plan、文書索引、READMEの参照関係。
- **変更**：Phase 3のマージとアーカイブを確認し、Product Specの4指標・7確認例を既存の集計、TUI、実ファイル、PTYテストへ対応付ける。Phase 4の進捗を「進行中」にする。
- **完了条件**：仕様文書との役割分担、相対リンク、差分の書式を確認する。Phase 3の過去資料を現行計画として扱わず、Phase 4の実装が終わる前に完了扱いしない。

### 4-1. 最小振り返り画面

- **対象**：`apps/pomodoro-tui/src/app.rs`の入力状態、`app/actions.rs`の通常キー、`ui.rs`と必要な小さな描画モジュール、App・PTYテスト、READMEの操作表。
- **変更**：`h`から4指標を開いて確認し、`h`／Escで戻る。狭い端末でも振り返りへの入口と閉じ方を示す。秒までの作業時間表示、空履歴、進行中、Pause・Distraction、完了後の値を確認する。
- **保存境界**：画面の開閉や再描画は保存を発生させない。tickによる現在のSessionの変化は反映し、保存待ちの未確定候補は反映しない。保存待ちになった場合は復旧操作を前面に出す。
- **テスト・完了条件**：Appの注入時計で表示値と`DomainState::reflection()`の一致、開閉中のtick、編集モード・保存失敗との入力優先順位、繰り返し描画の無副作用を確認する。複数の画面幅と高さでラベル・4値・閉じる操作または拡大案内が見えることを確認する。PTYで実行ファイルの`h`入力と終了を確認する。4-0に依存する。

### 4-2. 作業と選択結果の受入

- **対象**：`apps/pomodoro-tui/tests/workflow.rs`などの注入時計・実ファイル統合テスト、必要なApp／coreテスト、表示の不整合修正。
- **変更**：Quick Startの2分完了、選択待ち、通常Focusへの継続、Focusの25分完了を一つの保存履歴へつなぐ。作業時間27分、Focus自然完了1回、選択待ち時間0、Quick StartとFocusの別Session・継続関係を確認する。Focus途中中止では計時済み時間が残り、完了数が増えないことを確認する。
- **保存境界**：自然完了・選択・中止などの結果は保存確定後に表示し、通常tick由来の作業時間は採用中snapshotのライブ値として表示する。保存失敗と再試行でSession、event、ID、完了通知が重複しない。Quick Start継続先に設定されたFocus全時間が与えられる。
- **テスト・完了条件**：実時間で2分・25分待たず、注入時計で境界を進める。保存したV1ファイルを別のhandleで読み直し、Session・event・集計・画面表示を照合する。既存の`quick_start_completion_and_choice_match_saved_file_and_notification`と中止テストを拡張し、同じ境界を重複した独立テストで増やさない。4-1に依存する。

### 4-3. 中断・再起動・起動失敗の受入

- **対象**：`apps/pomodoro-tui/tests/lifecycle.rs`、`tests/terminal.rs`、`tests/startup.rs`、必要なcore／platformテストと表示の不整合修正。
- **変更**：Distraction申告後に終了・再起動して同じ中断をReturnで閉じ、Recovery Timeに終了中を含める一方、作業時間に含めないことを確認する。FocusとBreakのObservation Gapでは空白を加算せず手動再開を待つ。Quick Startの継続選択待ちは再起動後も選択待ちで、Focusを自動作成しない。
- **起動と保存**：新規データでは既定設定・Focus開始待ち・ラウンド進捗0・空履歴を確認する。未対応または破損した保存ファイルでは起動を止め、元ファイルを上書きしない。保存失敗中に表示する集計は採用済み状態を示し、再試行成功後だけ未確定候補の値を反映する。
- **テスト・完了条件**：既存の復元・PTY・不正ファイルテストを土台に、表示と保存したeventの接続で欠ける主張だけ追加する。Known／UnknownのRecovery Timeは仕様どおり区別し、Unknownを0とみなさない。PTYはキー経路と表示、注入時計と実ファイルは時間・履歴・再読込を確認する。4-1に依存し、4-2と独立に進められる。

### 4-4. 利用案内とPhase 4終了判定

- **対象**：README、実行計画、文書索引、PRの検証記録。
- **変更**：振り返りの開き方と4指標の意味、表示精度、保存失敗・復旧・再起動時の利用手順を実装に合わせる。4-2・4-3の受入結果をProduct Spec第10節の7例と照合する。
- **完了条件**：画面・README・仕様に未説明の差がなく、次節の終了条件を満たす。確認後にImplementation Planを「完了」へ更新し、本書を`docs/archive/`へ移して文書索引とリンクを直す。4-2・4-3に依存する。

## 4. Product Specの確認例と検証先

下表は検証の引継ぎ先を示す。既存テストの一部は個別のドメイン・保存境界を確認しているが、Phase 4では必要な箇所で操作から画面の値までつなぐ。

| Product Spec第10節のケース | 既存の主な証拠 | Phase 4で追加して確認する接続 | 単位 |
| --- | --- | --- | --- |
| Quick Start完了→Focus完了 | coreのQuick Start遷移、`tests/workflow.rs`の選択・保存 | 25分Focusの完了後に27分・Focus完了1回を保存ファイルと振り返り画面で照合 | 4-2 |
| Focus途中中止 | App／PTYの中止テスト、coreの終了結果 | 中止後・再起動後も作業時間が残り、完了数0と表示される | 4-2 |
| Distraction→終了→再起動→Return | PTYの申告・再起動・Return、coreの時間テスト | 同じ中断event、Return数、終了中を含むRecovery Time、作業時間除外を再読込と表示で照合 | 4-3 |
| Focus・BreakのObservation Gap | coreの空白判定、lifecycleの復元テスト | 空白を計時せず手動再開待ちとなることと、振り返りの作業時間を確認 | 4-3 |
| Quick Startの選択待ちで再起動 | PTYの選択待ち復元テスト | 再起動直後の表示と保存履歴に継続先Focusがなく、明示的選択後だけ作成される | 4-3 |
| 新規データで初回起動 | startup／lifecycleの新規作成テスト | 実行ファイルで既定設定・Focus開始待ち・ラウンド進捗0・4指標0を、保存ファイルで空履歴を確認 | 4-3 |
| 未対応形式・破損ファイルで起動 | startup／lifecycleの拒否・保全テスト | 停止理由と元バイト列の不変を確認し、空履歴への自動初期化がない | 4-3 |

## 5. 検証方法と終了条件

Rustを変更する各レビュー単位で、関連する決定的なテストに加えて次を通す。

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

時刻経過と保存失敗は注入して検証する。実ファイルは保存後の再読込と元ファイル保全、PTYは実行ファイルのキー入力と画面表示を確認する。保存層に変更が必要になった場合は保存境界の隔離クラッシュテストも実行する。Phase終了時には最低Rust 1.86でもビルドとテストを確認する。各PRには何を検証したかと、既存テストで担保する範囲を記す。

Phase 4は、次のすべてを満たしたときだけ完了とする。

- 4指標をTUIから確認でき、現在のSessionと保存再試行後の値もcoreの集計と一致する。
- Product Spec第10節の7例が、操作・保存・再起動・履歴・表示の該当する境界で検証されている。
- 画面とREADMEのキー案内、表示精度、起動失敗・保存失敗時の手順が一致している。
- 全workspaceと最低Rustバージョンの検証が通り、Phase 3の操作・V1保存契約に未説明の回帰がない。

Phase 4の完了までは拡張MVP全体を完成扱いしない。詳細履歴や追加統計の要望は、MVP後の利用結果に基づいて優先順位を判断する。
