# Phase 2 Plan

作成日：2026-09-17

本書は、Phase 2「永続化と復元の基盤」をレビュー可能な変更単位へ分けた実行計画である。対象、依存関係、互換対応、各単位の検証と完了条件を示す。実装済みであることを意味せず、関数・ファイル単位の完了台帳や検証結果は置かない。

Phase単位の進捗は[Implementation Plan](IMPLEMENTATION_PLAN.md)だけで管理する。機能の正本は[Product Spec](PRODUCT_SPEC.md)、状態と遷移の正本は[Domain Model](DOMAIN_MODEL.md)、保存契約の正本は[Persistence Schema](PERSISTENCE_SCHEMA.md)とし、本書で別の仕様を定義しない。

## 1. 到達点とPhase境界

Phase 2の到達点は「新しいDomainStateを安全に保存・復元でき、既存TUIがV1保存を使って動作し、保存失敗を成功として扱わない状態」とする。保存ライブラリの完成だけでは完了しない。

Phase 2では、既存の操作・設定・表示・通知を新しいモデルへ接続する。保存待ち、再試行、未保存終了、起動前の明示的バックアップ復旧を扱い、V1の全状態を壊さず復元できることを確認する。

Current Taskの新規入力、Quick Startの開始、Distractionの申告を日常操作として整えるのはPhase 3とする。ただし、Phase 2でも保存済みCurrent Taskの表示、復元したDistractionからのReturn、Quick Start選択待ちからの終了／継続には最小経路を用意する。未接続の状態を強制終了・自動選択・初期化で処理しない。

振り返りUIの完成とMVP全体の受入検証はPhase 4とする。既存の履歴欄を維持する場合は新モデルからの派生表示に置き換え、累計を「今日」と表示しない。旧DailySummaryは移行しない。

## 2. 変更対象と既存呼出元

新規モジュール・型名は責務を示す仮称であり、公開APIを固定するものではない。必要な境界だけを設け、新しいcrateや汎用フレームワークは追加しない。

| crate・境界 | 対象と責務 |
| --- | --- |
| pomodoro-core | `validation.rs`とドメインテスト。`DomainState::from_parts`の整合性検証を補強する |
| coreの既存モデル | `DomainState`、`Session`、`TimerState`、`Interruption`、`HistoryEvent`、ID型を原則維持。保存世代・I/O・再試行を追加しない |
| pomodoro-platformの保存境界 | 現行`storage`の`PersistedState`・`NativeStorage`をV1へ置換。内部に`schema_v1`／`codec`、`lock`、`atomic_save`、`recovery`の責務を分ける |
| platformの時刻・通知 | `time`でUTCと単調時計から`Observation`を作る。`notification`を新しい`SessionKind`と保存後の通知経路へ追従させる |
| pomodoro-tuiのアプリケーション境界 | `App`とUI非依存のcontrollerで操作候補、保存待ち、再試行、保存後の副作用を管理する |
| TUIの起動・描画・テスト | `main.rs`、`ui.rs`、startup test。ロック、復元、終了、既存入力と状態表示を接続する |
| 一時的な旧API | coreの`legacy`と旧timer／history／session、platformの旧保存API。全呼出元を切り替えた後に撤去する |

既存呼出元を壊さないため、V1の境界を旧APIと並行して追加し、まず一時ディレクトリを使うテストから呼ぶ。controller・表示・通知が揃ってから通常起動経路を一度だけV1へ切り替え、その後に旧APIを削除する。

これはコードの追加順による一時的な互換対応であり、保存データの互換機構ではない。同じ保存先への新旧の二重書込、旧状態からの変換、新旧状態の同期は行わない。

## 3. レビュー単位と依存関係

番号順を標準とする。2-4は2-0後、2-9はPhase 1と2-0後に独立して進められる。新しい型・APIを公開する変更には必要な呼出元追従を同梱し、coreだけ成功する状態を完成扱いしない。単位が大きくなればさらに分割するが、関連テストは後回しにしない。

### 2-0. 保存契約とPhase境界の補足

- **目的・対象**：Domain Model、Persistence Schema、Implementation Plan、README、本書の参照関係を揃える。
- **変更**：Activeの設定時間、履歴のライフサイクル、時計異常の証拠、厳密な日時・任意値・Current Task変換を補足し、Phase 2の最小TUI範囲を明記する。
- **互換対応**：文書のみ。保存フィールドや新しいプロダクト機能は増やさない。
- **確認**：文書間の整合性、相対リンク、差分の書式。未実装の検証を実装済みと記載しない。
- **完了条件・依存**：後続の実装判断の基準が揃う。Phase 1と設計レビューに依存する。

### 2-1. coreの読込検証を補強

- **目的・対象**：`pomodoro-core/src/validation.rs`、`domain_tests.rs`。保存済みの時計異常と中断時間の矛盾を拒否する。
- **変更**：中断が開いている間のeventに時計巻き戻りの証拠がある場合、終了時刻の差だけが正しいKnownを受理しない。eventの順序を検証するが、現在状態を再生・補正しない。
- **互換対応**：公開APIと既存呼出元は原則変更しない。
- **テスト（Unit）**：Distraction → AppClosing → 時計が戻ったAppRestored → Returnで生成した履歴のUnknownをKnownへ改変すると拒否すること。正当なKnown、Unknown、アプリ終了をまたぐReturn、時計が戻る正当な履歴は受理すること。
- **完了条件・依存**：不整合を拒否し、正常な遷移の生成物は引き続き検証を通る。2-0に依存する。

### 2-2. V1の基本値codec

- **目的・対象**：platformの`schema_v1`／`codec`。日時、ID、Settings、Current Task、enumの保存表現を扱う。
- **変更**：Persistence Schema §2.1の境界を実装する。ドメイン型へ無条件にSerdeを付けず、保存表現から検証して変換する。
- **互換対応**：旧保存APIとTUIはそのままビルド可能に保つ。
- **テスト（Unit）**：日時の上下限・精度・不正形式、整数範囲、未知variant、Settingsの範囲外、任意値のnullと欠落の違い、空・空白・前後空白・各行区切りを含むCurrent Task。
- **完了条件・依存**：正当な値は往復変換し、不正値は丸め・trim・補完せず拒否する。2-0に依存する。

### 2-3. Snapshot・Historyを含むV1全体codec

- **目的・対象**：`PersistedStateV1`とsnapshot・Session・Interruption・eventの保存DTO。
- **変更**：全体version、世代、保存候補日時、採番情報を含めて変換する。decode後は`DomainState::from_parts`と保存管理情報の検証を通す。
- **互換対応**：V1経路を追加するだけとし、旧形式へのフォールバックや中間保存形式は作らない。
- **テスト（Unit）**：全snapshot状態・種別・終了結果・eventの往復変換、全階層の未知フィールドと重複キー、versionなし・未対応version、参照・採番・区間合計・Active設定時間・Quick Start関連の不整合。
- **完了条件・依存**：snapshotを正本として全体を読み書きでき、情報を捨てて受理する経路がない。2-1、2-2に依存する。

### 2-4. 保存パスと排他ロック

- **目的・対象**：platformの保存パス、`lock`、必要な依存設定。複数起動による更新消失を防ぐ。
- **変更**：読込・初期化判定より前に専用`state.lock`を非ブロッキングでロックし、最終保存まで保持する。ファイルの存在ではなくカーネルのロックを使う。
- **互換対応**：V1境界に追加する。既存の最低Rustバージョンとsafeコード方針に適合するAPIを選び、依存導入を理由にMSRVを黙って引き上げない。
- **テスト（Integration）**：別プロセスの二重起動拒否、異常終了後の再取得、別保存先の独立性、子プロセスへロックを残さないこと。
- **完了条件・依存**：ロックの寿命を保存ハンドルに結び付け、終了時にlockファイルを削除しない。2-0に依存する。

### 2-5. 読込結果と書込許可の分離

- **目的・対象**：platformのload、`StorageError`、保存ハンドル。読込失敗後の初期状態による上書きを構造的に防ぐ。
- **変更**：新規、有効V1、復旧候補、未対応形式、破損、I/O失敗を区別する。ロックと有効な読込または新規判定が揃った場合だけ通常保存を許可する。
- **互換対応**：V1のテストから接続し、TUIの旧loadへ新しいエラーを無理に押し込まない。
- **テスト（Unit / Integration）**：本体なし、backupのみ、tempのみ、壊れた本体、有効な本体＋古いtemp、権限エラー、旧形式、未対応version。失敗後の元ファイル不変を確認する。
- **完了条件・依存**：load失敗から既定状態と通常書込許可を返す分岐がない。2-3、2-4に依存する。

### 2-6. 通常のatomic save

- **目的・対象**：platformの`atomic_save`、固定した保存候補。保存成功の境界を実装する。
- **変更**：内容・ID・世代・saved_atを固定し、本体と採用済み内容を比較する。検証済み本体のbackup、一意temp、ファイル同期、rename、親ディレクトリ同期の順に保存し、全成功後に世代を確定する。新規ディレクトリ作成の親側同期も含める。
- **互換対応**：既存経路の切替前にV1保存境界を独立検証する。
- **テスト（Unit / Integration）**：初回・連続保存、backup内容、同世代の外部変更、世代オーバーフロー、書込・同期・renameの各失敗位置。失敗注入をこの段階から用意する。
- **完了条件・依存**：renameのみを保存成功とせず、失敗位置を区別できる。汎用ファイルシステム抽象ではなく保存境界に限定した検証手段を用いる。2-5に依存する。

### 2-7. 再試行と確定不明

- **目的・対象**：保存候補、保存結果、再試行。rename後の同期失敗を安全に扱う。
- **変更**：本体が同じ候補なら再同期して同世代を確定、旧内容なら同じ候補を書き直し、第三の内容なら停止する。判定前にbackupを更新しない。
- **互換対応**：ドメイン操作ではなく、固定済み候補の保存を再試行するAPIを提供する。
- **テスト（Unit / Integration）**：各比較結果、繰り返す失敗、ID・event・世代・saved_at・JSONの不変、判定前のbackup保護。
- **完了条件・依存**：保存の再試行でドメイン遷移や採番が再実行されない。2-6に依存する。

### 2-8. 明示的バックアップ復旧

- **目的・対象**：platformの`recovery`。有効な.bakからの復旧を通常保存と区別する。
- **変更**：復旧元を検証し、明示確認の結果を受け、元本体を退避・同期する。復元遷移を一度だけ適用した候補を、.bakを更新しない復旧経路で保存する。採番・世代は復旧元系列から続ける。
- **互換対応**：確認画面は2-11で接続する。復旧元は直前の.bakだけとし、探索・枝の統合・旧形式の変換は追加しない。
- **テスト（Unit / Integration）**：本体破損・欠落、両方破損、拒否・キャンセル、元本体の読込・退避失敗、退避後の外部変更、復旧中の失敗・再試行、復旧後の通常保存。未対応versionを理由とする自動復旧を行わない。
- **完了条件・依存**：元ファイルと有効なbackupを保護し、失敗時も復元遷移を二重生成しない。2-7に依存する。

### 2-9. 実行時の時刻観測アダプター

- **目的・対象**：platformの`time`。UTC日時と単調時計からcoreの`Observation`を作る。
- **変更**：実行時アンカーと保存するUTC境界を分ける。通常観測と、保存失敗後など連続性の証拠が失われた観測を区別する。計時・gap判定をTUIへ複製しない。
- **互換対応**：旧時刻APIの呼出元は切替まで維持する。新しいruntime専用アンカーはV1へ保存しない。
- **テスト（Unit）**：正常経過、巻き戻り、長時間空白、単調時計の証拠不足、再起動時のアンカー破棄、閾値未満の短い保存失敗区間。テスト時刻を注入し、sleepに依存しない。
- **完了条件・依存**：証拠のない時間を加算せず、保存回復をAppRestoredで代用しない。Phase 1と2-0に依存する。

### 2-10. アプリケーション側の保存確定制御

- **目的・対象**：TUIのUI非依存controller／App境界。ドメイン遷移と操作成功を分離する。
- **変更**：最後の保存状態、通常計時中の状態、固定済み保存待ち候補を区別する。意味のある操作・自然完了は保存後に確定する。通常tickはチェックポイント対象とし、保存失敗中は通常操作と計時反映を保留する。
- **互換対応**：既存Appとは独立に検証してから接続する。coreへI/O・保存待ち専用Kind・通知を入れない。
- **テスト（Unit）**：Quick Start継続の再試行、自然完了、保存前の成功通知禁止、通知失敗による保存取消の禁止、checkpoint失敗、入力保留、中断の不確実性だけが変わるsnapshotの保存。
- **完了条件・依存**：保存回復後のRunning候補をObservation Gapへ移し、その遷移の保存も成功してから操作を許可する。二段目の保存失敗も再試行で重複しない。2-7、2-9に依存する。

### 2-11. 起動・復元・終了の接続

- **目的・対象**：controllerの起動・終了処理、復旧確認と終了結果。通常操作の前後も保存契約を守る。
- **変更**：ロック → 読込・検証 → RestoreApp → 保存確定 → 操作許可の順に接続する。復旧時は2-8で適用済みのRestoreAppを再適用しない。終了は観測後にCloseAppを適用して保存する。失敗時は再試行または明示的な未保存終了を案内する。
- **互換対応**：通常のmainへの切替は2-13aとする。復旧確認はTUIの通常操作開始前に行う。
- **テスト（Unit / Integration）**：全種別のRunning、全中断Kind、Ready、Quick Start選択待ちの復元。起動・終了・復旧の保存失敗と再試行、未保存終了の結果。
- **完了条件・依存**：再起動中を計時せず、Distractionや選択待ちを維持し、保存失敗を正常保存済みとして終了しない。2-8、2-10に依存する。

### 2-12. 既存TUIの表示・操作を新モデルへ追従

- **目的・対象**：TUIの`app.rs`、`ui.rs`、platformの`notification.rs`。保存確定制御を既存の利用経路へ接続できる状態にする。
- **変更**：既存キー操作を`Command`へ接続し、残り時間・ラウンド・中断理由をsnapshotから導出する。保存待ち・再試行・未保存終了と、復元したCurrent Task・Distraction・Quick Start選択待ちの最小表示と操作を用意する。
- **互換対応**：設定はReadyでだけ適用し、通知は新SessionKindへ追従させて保存後に呼ぶ。新旧Appの同期はしない。旧履歴欄を残すなら保存集計ではなく派生値へ置換する。
- **テスト（Unit）**：既存キー、Ready以外の設定拒否、Reset後の別Session、完了直前の入力を次Sessionへ流用しないこと、全復元状態の描画と操作経路、通知呼出順。
- **完了条件・依存**：新App経路をテストから操作でき、TUIが独自の計時・完了規則を持たない。2-10、2-11に依存する。

### 2-13a. 通常起動経路をV1へ切替

- **目的・対象**：TUIの`main`、platformの公開export、startup test、README。既存呼出元の接続を完了する。
- **変更**：通常起動を新しい保存・App経路へ切り替え、使われない旧APIはこの単位では削除しなくてよい。READMEを実際のV1動作と復旧・保存失敗時の案内へ更新する。
- **互換対応**：旧形式を移行せず、対応していないことを示して元ファイルを維持する。開発データも自動削除しない。
- **テスト（Integration）**：実ファイルによる起動・保存・再起動、復旧確認、二重起動、旧形式・未対応version拒否、保存各境界での子プロセス停止。startup testのファイル数固定assertは、元データ不変と許可されたlockファイル以外の不用意な生成がないことの検証へ変更する。
- **完了条件・依存**：通常実行経路がV1だけを使う。プロセス停止のテストだけで電源断まで保証したと扱わない。2-12に依存する。

### 2-13b. legacy撤去とPhase受入確認

- **目的・対象**：coreの`legacy`・旧timer／history／session、platformの旧保存・時刻API、不要な依存、関連文書。
- **変更**：呼出元がないことを確認して旧APIを撤去する。保持すべき回帰テストは新経路へ移し、テスト削除だけで通すことはしない。
- **互換対応**：切替後のコード整理として独立レビューする。共有中のSettingsなど必要な型は残す。
- **テスト（Unit / Integration）**：workspace全体、旧API参照の残存確認、§5の受入条件、最低Rustバージョンでの検証。
- **完了条件・依存**：通常経路・テストとも旧API依存がなく、§5の終了条件を満たしたうえでImplementation PlanのPhase進捗を更新できる。2-13aに依存する。

## 4. 主なリスクと対策

| リスク | 対策 |
| --- | --- |
| rename後の同期失敗を未保存と断定する | 確定不明を区別し、本体と候補を比較してから再試行する |
| 再試行でID・event・通知が重複する | 固定候補の保存と、ドメイン操作・保存後の副作用を分ける |
| 保存待ち時間を作業時間に含める | 観測の連続性を明示的に切り、gap遷移も保存してから操作を再開する |
| 復旧で有効なbackupを破損本体に置き換える | 通常保存と復旧保存を分岐し、元本体の退避とbackup維持を検証する |
| decode時に不正値が消える | 全階層の厳密なcodecと負例を、ファイル保存より先に検証する |
| 不確実性だけのsnapshot変更が保存されない | event数・elapsedだけで変更検知せず、controllerの回帰テストを置く |
| TUI追従がPhase 3へ先送りされる | 保存確定制御・起動終了・既存操作・V1切替をPhase 2の完了条件に含める |
| 単一JSONと全履歴検証の負荷 | 毎tickの全履歴encode・fsyncを避け、不要なcloneも確認する。DB化・履歴圧縮は先取りしない |
| 依存追加で最低Rustバージョンが崩れる | 依存選定時とPhase終了時にMSRVを確認する。未検証を成功扱いしない |

## 5. 検証とPhase 2終了条件

Rustを変更する各レビュー単位で、関連テストに加えて次を通す。

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

日時・観測・保存結果を注入するUnit testと、一時ディレクトリ・別プロセスを使うIntegration testを分ける。I/O失敗は書込・同期・renameの境界ごとに注入する。通常テストを実時間の長いsleepへ依存させない。

Phase 2完了には以下をすべて満たすことが必要である。各項目の逐次進捗は本書に転記せず、検証の証拠をテスト・PRに残す。

- V1の全状態・履歴が、情報を失わず保存・復元できる。
- 読込失敗・旧形式・未対応versionから自動初期化・上書きする経路がない。
